# 10 · Internacionalización

El producto es global desde el día uno ([ADR-0015](./adr/0015-i18n-nativo.md)).

## Alcance

- **Idiomas iniciales:** `en` (por defecto) y `es`.
- **Qué se traduce:** toda la web (landing, catálogo, docs, dashboard, legal), las descripciones del catálogo, las etiquetas de los tags y los componentes de Clerk.
- **Qué no se traduce:**
  - **La API** (`/v1/*`). Los mensajes de error van siempre en inglés: los lee una máquina, y así los usuarios encuentran respuestas al buscarlos.
  - Los IDs de modelo y los slugs de tags (`fast` siempre es `fast`; su etiqueta visible es "Fast" o "Rápido").
  - La moneda: **siempre USD**. Solo cambia el formato.

## Enfoque: el patrón nativo de Next 16, sin librería

Se sigue la guía de internacionalización que trae Next 16 (`node_modules/next/dist/docs/01-app/02-guides/internationalization.md`):

- **Segmento `[lang]`** en la raíz de `app/`: `src/app/[lang]/layout.tsx` es el root layout y pone `<html lang={lang}>`.
- **`generateStaticParams`** en el layout devuelve `[{ lang: "en" }, { lang: "es" }]`.
- **Diccionarios** en `src/lib/i18n/dictionaries/`, cargados con import dinámico solo en el servidor.
- **`next/root-params`:** `getDictionary()` lee el idioma con el getter `lang()`, sin pasarlo por props. Funciona en Server Components y utilidades de servidor. No funciona en Server Functions, Client Components ni Route Handlers.
- **Client Components:** reciben los textos ya traducidos como props desde su Server Component padre. No hay librería de i18n en el cliente.

Se descartó `next-intl` para el MVP. Ver [ADR-0015](./adr/0015-i18n-nativo.md).

### Diccionarios tipados

Los diccionarios son archivos `.ts`, no `.json`, para que TypeScript detecte claves faltantes:

```ts
// src/lib/i18n/dictionaries/en.ts — fuente de verdad de las claves
const en = {
  nav: { models: "Models", docs: "Docs", dashboard: "Dashboard" },
  tags: { fast: "Fast", reasoning: "Reasoning" /* … */ },
};
export type Dictionary = typeof en; // mismas claves, valores string
export default en;

// src/lib/i18n/dictionaries/es.ts
import type { Dictionary } from "./en";
export default {
  nav: { models: "Modelos", docs: "Docs", dashboard: "Panel" },
  tags: { fast: "Rápido", reasoning: "Razonamiento" /* … */ },
} satisfies Dictionary;
```

Si falta una clave en `es`, `pnpm typecheck` falla.

## Rutas y detección de idioma

- **Todas las páginas llevan prefijo:** `/en/models`, `/es/models`, `/es/dashboard/keys`.
- **`src/proxy.ts`** (en Next 16, `middleware` se llama `proxy`): si la ruta no trae idioma, redirige a:
  1. el idioma de la cookie `NEXT_LOCALE`, si existe;
  2. si no, el mejor match de `Accept-Language` entre los idiomas soportados (con `@formatjs/intl-localematcher` + `negotiator`, como en la guía);
  3. si no, `en`.
- **El matcher del proxy excluye** `/v1/*`, `/api/*`, `/_next/*` y los archivos estáticos, y el proxy no actúa en el host `api.cheaptokens.wtf` ([ADR-0026](./adr/0026-marca-cheaptokens-wtf.md)). La API no pasa por i18n ni por Clerk.
- **El mismo `proxy.ts` también ejecuta `clerkMiddleware`.** Solo hay un proxy por proyecto, así que la lógica de idioma y la de Clerk se componen ahí. Protege `/:lang/dashboard(.*)`, pero cada página privada vuelve a verificar con `auth()` ([03 · Arquitectura](./03-arquitectura.md#web-dashboard)).
- **El selector de idioma** cambia el prefijo de la ruta actual y guarda la cookie `NEXT_LOCALE`.

## Formatos

Se usan siempre las APIs `Intl` con el idioma de la ruta. Nunca se arman formatos a mano:

| Qué | API | `en` | `es` |
|---|---|---|---|
| Dinero | `Intl.NumberFormat(lang, { style: "currency", currency: "USD" })` | `$0.30` | `0,30 US$` |
| Tokens | `Intl.NumberFormat(lang, { notation: "compact" })` | `200K` | `200 mil` |
| Fechas | `Intl.DateTimeFormat(lang, { dateStyle: "medium" })` | `Nov 8, 2026` | `8 nov 2026` |
| Porcentaje | `Intl.NumberFormat(lang, { style: "percent" })` | `90%` | `90 %` |

> En las columnas de precio, `0,30 US$` puede ocupar más ancho que `$0.30`. Hay que revisar el layout de la tabla del catálogo en los dos idiomas.

## Contenido del catálogo

- `models.description` es `jsonb` por idioma: `{ "en": "...", "es": "..." }`.
- Si falta un idioma, se usa `en`. La sincronización **advierte** (no falla) si falta `es`.

## Clerk

- `ClerkProvider` recibe la localización según `lang` (paquete `@clerk/localizations`, por ejemplo `esES`).
- Las rutas de Clerk también llevan idioma: `/[lang]/sign-in` y `/[lang]/sign-up`.

## Checkout de pagos

- El checkout del MoR se abre en el idioma del usuario cuando el MoR lo permite. Los recibos y facturas los emite el MoR ([ADR-0019](./adr/0019-merchant-of-record.md)).

## Implementación (2026-11-08)

- Configuración y negociación: `src/lib/i18n/config.ts` (`LOCALES`, `negotiateLocale`, `switchLocalePath`).
- Diccionarios: `src/lib/i18n/dictionaries/{en,es}.ts`. El tipo `Dictionary` sale de `en` y obliga a `es` a tener las mismas claves; además una prueba verifica que los marcadores `{x}` coincidan.
- Idioma en cualquier Server Component, incluida la 404: `getLocale()` en `src/lib/i18n/server.ts`, sobre `next/root-params`.
- `src/proxy.ts` redirige las rutas sin idioma. Clerk se compone ahí cuando llegue.

## Migración del scaffold actual

El scaffold tiene `src/app/layout.tsx` con `lang="es"` fijo y `src/app/design-system/page.tsx`. Al implementar i18n:

1. ~~Mover el layout a `src/app/[lang]/layout.tsx` con `lang` dinámico.~~ Hecho.
2. ~~Mover `design-system` y `page.tsx` debajo de `[lang]/`.~~ Hecho. Las páginas públicas viven en el grupo `src/app/[lang]/(site)/`, que agrega el header y el footer.
3. Dejar `src/app/v1/` y `src/app/api/` fuera de `[lang]/`. Los route handlers no necesitan layout.

## Agregar un idioma

1. Agregar el código a la lista de idiomas soportados.
2. Crear su diccionario. TypeScript obliga a completar todas las claves.
3. Agregar descripciones del catálogo en ese idioma (opcional, hay fallback a `en`).
4. Agregar la localización de Clerk.
5. Revisar el layout con textos más largos (el alemán y el portugués suelen ser los más largos).
